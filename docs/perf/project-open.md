# Desktop project-open performance

## Budgets

The desktop targets are measured from the user's open/create gesture:

- New project: runtime `/health` 2xx and the project workspace mounted in the
  renderer within 1,000 ms at p95.
- Existing project: runtime `/health` 2xx, the first workspace file listing,
  and a chat request accepted within 6,000 ms at p95.
- Warm switch-back: under 1,000 ms at p95.

The strict new-project target requires a prepared workspace and a pre-booted
runtime. A cold install or Bun process spawn cannot meet 1 second on typical
Windows hardware.

## Measurement

Start the packaged desktop app with `SHOGO_PERF_LOG=1`. The UI records marks on
`globalThis.__shogoColdStart__` and sends `x-shogo-open-id` on readiness
requests. API, worker, and agent-runtime logs emit matching one-line JSON
records prefixed with `[shogo-perf]`.

Headless API benchmark:

```powershell
$env:SHOGO_BENCH_PROJECT_ID = "<existing-project-id>"
bun run bench:open --scenario existing-cold --project-id $env:SHOGO_BENCH_PROJECT_ID --runs 5
bun run bench:open --scenario existing-warm --project-id $env:SHOGO_BENCH_PROJECT_ID --runs 5
```

For a new-project run, provide `--workspace-id` and `--user-id` and add
`--cleanup` so the perf projects (DB row and workspace directory) are removed
afterwards. For a folder-bound project, provide `--folder` and
`--workspace-id`. Use `--api-url`, `--workspaces-dir`, and
`SHOGO_BENCH_COOKIE` when the API needs explicit connection/auth settings.
For a local-mode API, the harness automatically calls
`/api/local/auto-sign-in` when no cookie is supplied; set
`SHOGO_BENCH_AUTO_SIGN_IN=0` to require an explicit cookie.

Readiness probes go through `/api/projects/:id/agent-proxy/*`, the same path
the renderer uses. The runtime's direct port gates `/agent/*` behind a runtime
token, so probing it from outside the app 401s forever. `totalMs` is the
gesture-to-responsive number: create/reopen start until the workspace tree is
served.

`existing-cold` needs `--cold-mode` because `POST /runtime/stop` is a no-op for
pool-assigned runtimes and leaves the project warm:

- `kill`: SIGKILL the process serving the project, then reopen. With an idle
  pool runtime available this measures the pool-hit reassign path.
- `kill-pool`: also SIGKILL every idle pool runtime (`/health` reports
  `poolMode: true`) so the reopen is a true cold spawn.

Add `--pause-ms 65000` between cold runs on builds that still have the 60 s
startup-grace behaviour described below. Results are written as JSON and
Markdown under `bench-results/` with p50/p95/max phase values.

For a structured desktop log, render a correlated waterfall:

```powershell
bun run bench:waterfall --log "$env:LOCALAPPDATA\Shogo\logs\main.log" --open-id <id>
```

Renderer-inclusive capture:

```powershell
$env:PLAYWRIGHT_E2E = "1"
$env:SHOGO_PERF_E2E_PROJECT_ID = "<existing-project-id>"
npx playwright test --config apps/desktop/e2e/playwright.config.ts e2e/project-open-perf.spec.ts
```

Run each scenario at least five times on a packaged build on Windows and
macOS. Record host RAM, app cold/warm state, Node availability on Windows,
`HOST_WARM_POOL_SIZE`, and whether Defender real-time protection is enabled.
Do not compare a development API or a warm runtime with a packaged cold run.

## Windows baseline (packaged 1.14.1, 2026-09-10)

Host: Windows 11 Pro, i9-14900K, 64 GB RAM, Defender real-time protection on,
Node 22 / npm 11 on PATH, `HOST_WARM_POOL_SIZE=1`, `maxAssigned=2`. API-level
numbers from `bun run bench:open` against the installed desktop app; the
renderer is not included. Raw files land in `bench-results/` (gitignored) and
are regenerated by the commands above.

| Scenario | Runs | totalMs p50 | totalMs p95 | Budget | Dominant phase |
|---|---:|---:|---:|---:|---|
| existing-warm (switch back) | 3 | 9 | 10 | 1,000 | none |
| existing-cold, pool hit (`--cold-mode kill`) | 3 | 671 | 702 | 6,000 | `/pool/assign` + gateway start |
| existing-cold, pool miss (`--cold-mode kill-pool`) | 2 | 2,389–2,475 | — | 6,000 | bun spawn 0.5 s to `/health`, gateway ready at ~1.5 s |
| new project, warm npm cache | 2 | 20,614–21,021 | — | 1,000 | `npm.cmd install` 20.0 s |
| new project, cold npm cache | 1 | 65,256 | — | 1,000 | `npm.cmd install` 65 s (76 s in the app's own first create of the day) |
| runtime dies < 60 s after assign | 4 | 58,516 | 58,727 | 6,000 | startup-grace window, see below |

Phase detail for a new project (from `main.log`): template copy 70–120 ms,
`pkg.installAsync` 20,014 ms (warm cache) / 76,083 ms (cold), `/pool/assign`
640 ms, gateway started ~1 s later. Creating the DB row is 8–70 ms.

Findings that change the plan:

1. Runtime boot is not the problem on this class of machine. A true cold spawn
   reaches `/health` in ~0.5 s and serves the workspace tree in ~2.4 s; the
   pool-hit path is ~0.7 s. Both are inside the 6 s budget. The 8–12 s
   "Windows cold boot" figure in the worker's comments does not reproduce here.
2. New-project time is entirely `npm install` into a fresh copy of the
   template. The pre-seeded warm workspace in this checkout is the fix; it must
   be verified on a packaged build of this branch, not on 1.14.1.
3. `HostWarmPoolController.getProjectUrl()` returned a dead runtime's URL for
   the whole 60 s `STARTUP_GRACE_MS` window. Any crash, OOM kill, or pool
   eviction within a minute of assignment left `sandbox/url` reporting
   `ready: true` while every agent-proxy call failed for ~58 s. Fixed in this
   checkout: the controller now listens for the child `exit` event and checks
   `exitCode`/`signalCode` before honouring the grace window
   (`apps/api/src/lib/__tests__/host-warm-pool-dead-runtime.test.ts`).
4. `maxAssigned` computed to 2 on a 64 GB host (`freeMB / (2 × memCeil)` with
   `memCeil=8192`). Opening a third project evicts the least-recently used one,
   so switching between three projects is a reassign every time instead of the
   9 ms warm path. Fixed in this checkout: `computeMaxAssignedFor` sizes by an
   expected ~1.5 GB footprint instead of the kill ceiling (8 on this host,
   still clamped by `HOST_POOL_MAX_HARD_CAP`); `HOST_POOL_MAX_ASSIGNED` still
   overrides.
5. `POST /runtime/stop` does not stop pool-assigned runtimes; the UI's stop
   action is a no-op for them. Fixed in this checkout: `RuntimeManager.stop`
   also evicts the project from the host pool.
6. Pool runtimes in 1.14.1 log `runtime-template not found in any candidate
   path` and `Tech stack "react-app" not found`, and one pool boot crashed with
   an uncaught exception in `isServerConfig(entryNamespace?.default)`. The pool
   still serves projects because `/pool/assign` re-seeds, but each is a wasted
   boot.
7. 1.14.1's `DELETE /api/projects/:id` removes the row but leaves the seeded
   workspace and `node_modules` on disk; the harness cleans up after itself.

A packaged macOS run is still required; the source comments' 3–5 s figure for
macOS is context, not a measurement. (Source-level macOS numbers are now
available — see the macOS section below.)

## Implemented latency reductions

1. The desktop warm pool is enabled by default on hosts with at least 4 GB of
   RAM. Its controller prepares one dependency-installed workspace before its
   first claim.
2. `RuntimeManager` maintains a `.warm/.ready` workspace. New default-stack
   projects claim it using a same-volume rename; if preparation is not ready,
   the existing seed/install path remains the fallback.
3. Existing project cards, list rows, and sidebar project names prewarm on
   pointer/tap intent. The desktop API also prewarms the most recently updated
   project after launch, bounded by `DESKTOP_STARTUP_PREWARM_PROJECTS`.
4. Packaged desktop builds compile a standalone agent-runtime with Bun
   `--compile --bytecode` when possible, retrying `--compile` without bytecode
   because the runtime uses top-level await, and retain the JS bundle as a
   final fallback.
5. The UI no longer mounts Monaco's Workbench while the IDE tab is hidden.
6. Windows installs can be compared with
   `SHOGO_WINDOWS_INSTALL_BACKEND=bun`; the default remains npm for the
   existing empty-node-modules mitigation.
7. Host warm pool: a runtime that exits is evicted on the child `exit` event
   and never returned during the startup grace; `maxAssigned` is sized from an
   expected footprint rather than the kill ceiling; `RuntimeManager.stop`
   evicts pool-assigned runtimes.

## Benchmarking this checkout (not the installed app)

`bun run bench:local-api` boots the checkout's API in local mode on port 39200
with scratch data under `%TEMP%\shogo-bench\data` (own SQLite, workspaces,
`_template`, `HOST_WARM_POOL_SIZE=1`, `SHOGO_PERF_LOG=1`) and prints a
ready-made `bench:open` command with the workspace and user ids. Pass
`--reset` to wipe the scratch data, `--pool-size N`, or `--env K=V`. The API
log is `%TEMP%\shogo-bench\data\api.log`. The pool spawns the agent-runtime
from `packages/agent-runtime/src/server.ts` but resolves the other packages
through their `dist` outputs, so run `bun run build:packages` after touching
`packages/*` or the pool boots fail with missing exports.

New-project phase detail: DB row 8–18 ms, `sandbox/url` ready 170–300 ms
(warm-workspace rename ~20 ms, `/pool/assign` in the runtime 36–108 ms, the

120–470 ms, gateway ready 25–210 ms later, tree listing ~20 ms.

### Root causes fixed while getting there

1. Every desktop project committed `node_modules`. The template copy filters
   in `apps/desktop/src/local-server.ts` and `RuntimeManager` used
   `src.includes('.git')`, which also dropped `.gitignore`. The installed
   1.14.1 `_template` has no `.gitignore`; its projects track 36–38k files and
   carry 125–162 MB `.git` directories. The first `git add -A` inside
   `/pool/assign` took over 60 s, tripping the assign timeout and falling back
   to a cold spawn, and every later commit and LFS pass paid for it too.
   Fixed: segment-based `isTemplateCopyExcluded`, `_template` self-heals its
   `.gitignore`/`.gitattributes`, `ensureWorkspaceGitignore` restores a missing
   ignore on open, `seedRepoIfAbsent` writes a default ignore when dependency
   dirs already exist, and the runtime's bootstrap runs `untrackDependencyDirs`
   to drop already-committed `node_modules`/`dist` from the index.
2. Idle pool runtimes had no `WORKSPACE_DIR`, so `/app/workspace` resolved to
   a real `C:\app\workspace` on the system drive. They pre-seeded there,
   ran `npm install` in it (`EUNSUPPORTEDPROTOCOL workspace:*`), and picked up
   stale `.shogo-pool-assignment` markers. Fixed: each pool runtime gets a
   private scratch dir under `<workspaces>/.pool/<id>` (removed on destroy) and
   `SHOGO_POOL_SKIP_PRESEED=1`, because the API prepares the real workspace at
   assign time. A leftover `C:\app\workspace` from older builds is harmless
   but can be deleted by hand.
3. `isPortFree` in the pool controller did a bind-and-close probe. Under Bun on
   Windows the listener leaked inside the API process, so every replacement
   pool boot after a claim died with `EADDRINUSE` on the port the API itself
   held. Fixed: connect-based probe.
4. `resolveProjectPodUrl` could hand a pool runtime to a project that already
   had a live direct runtime (two runtimes per project). Fixed: the pool branch
   is skipped when a direct runtime is running or starting.
5. `/pool/assign` did the local git seed and LFS pass on the critical path
   (~1 s). The agent-runtime now initialises the git layer in the background
   when there is nothing to restore from a store; turn-complete commits wait on
   `gitLayerReady`.
6. Rebuilding the `.warm/.ready` workspace after each claim ran a full
   `npm install` (68–75 s here). A second new project inside that window paid
   the whole install. Now the template's dependencies are installed once into
   `<workspaces>/.warm/.deps` (keyed by template manifest + platform, so an
   app upgrade rebuilds it) and every warm workspace or cold seed clones
   `node_modules` from it (`apps/api/src/lib/runtime/clone-tree.ts`, 40k files
   in 9–18 s on this host) — hard-linked by default here, APFS-clonefile'd on
   macOS (see the macOS section below); `SHOGO_DEPS_CLONE_MODE=copy` forces
   copies, `SHOGO_DEPS_STORE=0` disables the store. A create that arrives
   while the clone is in flight waits for it (bounded by
   `SHOGO_WARM_WORKSPACE_WAIT_MS`, default 90 s) instead of starting a
   competing install.

## macOS results on this checkout (2026-09-11)

Host: Apple M5 Max (arm64), 128 GB RAM, macOS (Darwin 25.5), APFS root volume.
Dev API via `bench:local-api`, agent-runtime run from source (not the
compiled binary), `HOST_WARM_POOL_SIZE=1`. All numbers below are p50/p95/max
over 5 runs unless noted.

| Scenario | Runs | totalMs p50 | totalMs p95 | Budget | Dominant phase |
|---|---:|---:|---:|---:|---|
| new project, first create of the session (builds `.deps` store + warm clone) | 1 | 3,926 | — | 1,000 | `bun install` into `.warm/.deps` (13.1 s) + `.warm/.ready` clone (2.7 s), overlapped with the claim |
| new project, warm workspace ready | 5 | 251 | 3,926\* | 1,000 | `sandbox/url` → `resolveProjectPodUrl` (\*p95/max dominated by the one first-of-session run above; steady-state max was 254) |
| existing-warm (switch back) | 5 | 7 | 11 | 1,000 | none |
| existing-cold, pool hit (`--cold-mode kill`) | 5 | 175 | 176 | 6,000 | `/pool/assign` + gateway start |
| existing-cold, pool miss (`--cold-mode kill-pool`) | 5 | 1,178 | 1,179 | 6,000 | bun spawn to `/health` |

Every scenario is comfortably inside budget on this hardware — better than
the Windows numbers above on every scenario, consistent with the faster CPU,
NVMe, and (after the fix below) APFS clone-on-write. The "historical 3–5 s"
figure referenced in the source comments does not reproduce here at the
source level; a packaged-build run (below) is still needed to rule out
Gatekeeper/codesigning first-launch overhead on a `.app` bundle.

### Root cause fixed on this checkout

`clone-tree.ts`'s default `link` mode hard-links every file. Hard links work
correctly on APFS, but two things made them the wrong default for macOS:

1. **Slower.** Cloning the `.deps` store's 36,907-file `node_modules` into a
   fresh `.warm/.ready` workspace — which happens in the background after
   *every* `new`-project claim, to re-arm the next one — measured 9.4 s
   hard-linked vs 3.2 s using APFS's `clonefile(2)` (`fs.copyFile` +
   `COPYFILE_FICLONE`), confirmed independently with `cp -al` (10.4 s) vs
   `cp -c` (5.6 s) on the same directory. This showed up directly in the
   `new` scenario: the first create of a session (which also builds the
   `.deps` store) dropped from 12,291 ms to 3,926 ms `totalMs` end to end.
2. **Riskier.** A hard-linked clone shares one inode with the store; a tool
   that opens-and-truncates-in-place (rather than the unlink+rewrite a package
   manager uses) would corrupt the store for every other clone. A `clonefile`
   clone is copy-on-write — same near-zero cost and no extra disk as a hard
   link, but a fully independent file from the moment it's created.

Fixed: `clone-tree.ts` gained a `ficlone` `CloneMode` and a
`defaultCloneMode()` helper that returns `'ficlone'` on `darwin` and `'link'`
everywhere else (Windows/Linux behavior, and the Windows numbers above, are
unchanged). `SHOGO_DEPS_CLONE_MODE` still accepts `link` / `ficlone` / `copy`
to override. `COPYFILE_FICLONE` (unlike `_FORCE`) degrades to a plain copy
instead of throwing when a volume doesn't support cloning, so requesting it
is safe even off APFS — the platform gate just avoids paying for a request
that can't help elsewhere. See
[apps/api/src/lib/runtime/clone-tree.ts](apps/api/src/lib/runtime/clone-tree.ts)
and its test for the fallback chain (`ficlone` → `link` → `copy`, matching the
existing Windows/Linux `link` → `copy` chain).

## Next decisions from the benchmark

- If the p95 new-project claim is above 1 second, inspect
  `warm-workspace:ready`, `pool/assign`, and `health-first-response` first.
  The likely issue is warm-pool starvation or a first-run workspace install.
- If existing cold opens exceed 6 seconds after the warm pool is healthy,
  compare the standalone binary with the JS fallback and inspect the
  `agent-first-output` to `agent-health-ready` interval.
- If `/health` meets budget but chat or files do not, keep the runtime
  readiness gate and inspect `/ready/gateway`, gateway initialization, and
  post-health PreviewManager/LSP work. Do not declare the project responsive
  from a TCP listener alone.
- Do not add Defender exclusions automatically. They change machine security
  policy and require explicit user/IT approval; measure with the existing
  workspace and Bun paths first, then document an opt-in recommendation if
  antivirus scanning is shown to dominate.
