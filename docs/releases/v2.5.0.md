# Shogo 2.5.0 release plan

Release plan, test plan and rollback notes for **v2.5.0**, the first minor since
v2.4.0. Requested by Russell in #go-live on 2026-11-05 ("prepare a 2.5.0
release"). Tracked on **REL-4**.

- **Previous production tag:** `v2.4.11` → `16ca77bd2` (shipped 2026-11-03
  16:02Z; production and staging `/api/health` both report `2.4.11`).
- **Candidate release commit:** `main` @ `9dd29e5d3` (2026-11-04 19:19Z).
- **Why a minor:** this range has features (Knative publishing with
  environments, one Personal workspace per account, per-seat AI allowance,
  edge-only user-app proxies) and 5 + 5 migrations. Per
  `apps/docs/changelog/_README.md` a minor gets a What's New entry, which rolls
  up everything shipped in v2.4.1–v2.4.11, and an announcement email. Both are
  drafted in this PR.

## Release blockers (decide before the tag)

| **B1** | **#1919 (SHO-312) halves live Business allowances at the old price** | `ROLLING_WINDOW_LIMITS.business` on `main` is `$4.60/wk` per seat (was `$9.90/wk` per seat, pooled). The PR body, Dev 1 and QA all said it must not reach production before Phase 5 (new Stripe prices `$8`/`$16` and grandfathering). Phase 5 has not landed: nothing in `stripe-prices.ts` / `regional-plan-pricing.ts` changed since v2.4.11, and the Business price is still `$40/seat`. Production today: **5 active Business subscriptions (6 seats) and 9 trialing (10 seats)** would lose 54% of their weekly window at the same price. Basic (4 active) goes `$1.90 → $2.30/wk`, which is better for them; Pro (15 active) is unchanged | **(a) recommended:** small PR that keeps the per-seat counters but puts the ladder back to the live values (basic `$1.90`, business `$9.90` per seat), so no one loses allowance, and moves the `$2.30`/`$4.60` ladder to the Phase 5 PR. **(b)** land Phase 5 (Stripe prices + grandfathering + email) before tagging. **(c)** ship as-is (not recommended) |

## Migrations

All five are additive. Two carry backfills that rewrite rows; none drop or
rename anything, so the old code ignores them on rollback.

| Track | File | What | Risk |
| --- | --- | --- | --- |
| Postgres + SQLite | `20261104120000_sho285_one_personal_workspace` | `workspaces.personalOwnerId` (unique), backfilled with each user's oldest Personal, cloud first; `agent_schedules.runOnInstanceId` and `agent_configs.runOnInstanceId`, pinned to the hosting desktop for hosted workspaces | low. The backfill picks one workspace per user with `DISTINCT ON`, so the unique index cannot collide; `agent_schedules` has 0 rows in prod |
| Postgres + SQLite | `20261104120000_sho308_published_environments` | `published_environments`, `published_deployments`, `published_usage_minutes`; backfills a `production` environment for every published project (`publishedAlwaysOn` → min scale 1) | low. New tables; the backfill is one insert per published project with `ON CONFLICT DO NOTHING` |
| Postgres + SQLite | `20261104120000_sho311_analytics_indexes` | three `createdAt` / `(memberId, createdAt)` indexes | **high unless built first** (B2). Plain `CREATE INDEX` on a 41 GB table at api boot |
| Postgres + SQLite | `20261104120000_sho312_per_member_usage_windows` | four window columns on `members` with defaults | low. 988 rows |
| Postgres + SQLite | `20261104140000_sho308_published_db_schema` | `published_environments.dbSchema` / `dbSchemaHash` | low. Nullable, new table |

B2 statements, run on the primary of `platform-pg` in **production-us** and
**production-eu** (and staging if they are missing there):

```sql
CREATE INDEX CONCURRENTLY IF NOT EXISTS "tool_call_logs_createdAt_idx" ON "tool_call_logs"("createdAt");
CREATE INDEX CONCURRENTLY IF NOT EXISTS "usage_events_memberId_createdAt_idx" ON "usage_events"("memberId", "createdAt");
CREATE INDEX CONCURRENTLY IF NOT EXISTS "chat_messages_createdAt_idx" ON "chat_messages"("createdAt");
```

Check afterwards that none is `INVALID` (`SELECT indexrelid::regclass FROM
pg_index WHERE NOT indisvalid;`). If one is, drop it and build it again.

## Config and infrastructure

- **New env (all optional, all `optional: true` in the overlays):**
  `SHOGO_EDGE_PROXY_SECRET` (unset: nothing enforced), `PROJECTS_DB_ADMIN_URL`
  (from `projects-pg-superuser`), `PROJECTS_DB_POOLER_HOST` (set on staging
  only; unset in prod by design), `PUBLISH_POSTGRES` (unset: auto).
- **Publishing substrate changes in production.** Production publishes went to
  metal because `SHOGO_METAL_ALL_PROJECTS=true`. From 2.5.0 new and re-published
  sites go to Knative. Knative Serving is healthy in production US (activator,
  autoscaler, controller, kourier, webhook all 1/1; 111 ksvcs in
  `shogo-production-workspaces`). EU should be checked the same way before the
  tag. Rollback is `PUBLISH_SUBSTRATE=metal` via
  `.github/scripts/sync-api-env.sh`, no data move.
- **k8s / terraform in this range:** `k8s/cnpg/*/projects-pooler.yaml` (prod
  poolers front a cluster that does not exist there yet, so they are not
  applied), `k8s/cnpg/staging-oci/projects-cluster.yaml`, edge Worker changes in
  `terraform/modules/preview-router` and `publish-hosting-oci` (header stamping
  only, inert without the secret).
- **Open, related, not in this release:** #1892 keeps the Knative activator off
  always-on published services in production (`UNSTABLE`). With publishing moving
  to Knative it matters more; worth landing before or soon after the tag.

## Test plan

1. **CI on the release commit.** `ci.yml` and `Build, Test, and Deploy` green on
   the commit that gets the tag (re-check if #1931 or the B1 fix lands first).
2. **Staging pass.** Work through the "Test on staging" column above. The
   publishing, Personal-merge and per-seat rows need a real staging account and
   a desktop pointed at staging; the rest can be done in a browser and on a
   phone.
3. **Desktop.** Pairing and the Personal merge are desktop-only. Build the
   staging desktop from the release commit and pair it to an account that has
   its own local Personal.
4. **Phone.** Android background push and the workspace-link guard on a real
   device.

## Tagging

1. Resolve B1 and B2. Freeze the release commit (the B1 fix commit, or
   `9dd29e5d3` plus anything merged before the freeze) and update REL-4.
2. `git tag -a v2.5.0 -m "Shogo 2.5.0" <release-commit> && git push origin v2.5.0`.
3. Watch `deploy.yml`: promote-images → deploy-us → deploy-eu →
   metal-runtime-image → dispatch-metal-agent-release → SDK publish. The tag also
   starts `desktop-release-macos.yml`, `desktop-release-windows.yml`, the CLI /
   worker tarballs and the Android/iOS workflows (the mobile version is taken
   from the tag). `finalize-release.yml` un-drafts the GitHub release only when
   all four asset workflows succeed; if one is red, fix it, re-run it, then
   re-run `Finalize Release`. Do not re-tag.
4. Post-deploy: `/api/health` reports `2.5.0` in US **and** EU; one static and
   one server publish in production; open `/admin/analytics`; no new SigNoz
   alerts for an hour; `@shogo-ai/sdk@2.5.0` is `latest` on npm.
5. Merge this PR so the changelog entry ships with the next docs deploy, then
   send the email below.

## Rollback

- **App / API:** redeploy `v2.4.11` through `deploy.yml`. The new columns and
  tables are ignored by the old code. Leave the SHO-311 indexes in place.
- **Publishing only:** set `PUBLISH_SUBSTRATE=metal` with
  `.github/scripts/sync-api-env.sh shogo-production-system PUBLISH_SUBSTRATE metal`
  (US and EU). New publishes go back to metal; sites already moved to Knative
  keep serving until re-published or moved back with
  `scripts/migrate-published-to-knative.ts`.
- **Personal merge:** a merge rewrites rows and moves files under
  `merged/<device>/`; nothing is deleted, but it is not undone by a rollback.
  Pause pairing of 2.5.0 desktops if merges go wrong.
- **Desktop:** the `v2.4.11` installers stay on that release. If the release is
  published broken, `gh release edit v2.5.0 --draft` hides it; keep the tag.
